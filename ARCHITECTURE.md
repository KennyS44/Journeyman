# Архитектура Journeyman

Разбор решений: как устроены слои, куда и почему текут данные, почему хранилище
на IndexedDB, а калькулятор — на рекурсивном спуске, а не на `eval`.

Приложение целиком статическое: сервера нет, сборки нет, зависимостей нет —
около 3600 строк на HTML, CSS и JS плюс 630 строк тестов.

---

## 1. Слои и кто кого знает

Стрелка означает «вызывает»; обратных вызовов нет ни одного.

    index.html                                       порядок <script> задаёт слои
        │
        ├── js/db.js      DB      хранилище. Не знает про DOM ни строчки.
        ├── js/ui.js      UI      DOM-помощники: el, icon, окна, sanitize, blobUrl.
        │                         Не знает про DB и про экраны.
        ├── js/zip.js     ZIP     чтение и запись zip. Чистые байты, DOM не нужен.
        ├── js/backup.js  BACKUP  кодекс в файл и обратно. Знает DB, UI и ZIP.
        ├── js/calc.js    CALC    парсер выражений + два виджета.
        │                         Чистая функция evaluate() и DOM-обвязка вокруг.
        ├── js/demo.js    DEMO    демо-сцена первого запуска. Знает только DB.
        ├── js/app.js     APP     оболочка: маршруты, шапка, мини-плеер, teardown.
        │                         Знает имена трёх экранов — и только их.
        │
        └── js/screens/           экраны. Каждый знает DB, UI, APP; про соседей — нет.
              menu.js   MENU  →  #/          список пространств
              space.js  SPACE →  #/s/<id>    холст: карточки, нити, масштаб
              node.js   NODE  →  #/n/<id>    текст объекта, панели, свиток плана

Правило, которое держит всё это в порядке: **зависимости идут строго вниз**.
`DB` не знает, что существует экран; `UI` не знает, что существует хранилище;
экран не знает про другой экран. Переход между экранами — только через
`APP.go('#/...')`, то есть через адресную строку.

Отсюда бесплатно получаются две вещи. Первая — парсер тестируется в Node без
браузера (`tests/calc.test.js` подгружает `calc.js` через `vm` и дёргает
`evaluate`, потому что тот ничего не знает о DOM). Вторая — экран можно
переписать целиком, не открывая остальные файлы: наружу он отдаёт ровно одну
функцию `render()`.

Размеры после разбиения (было — 1221 строка в одном `app.js`):

| файл | строк | ответственность |
|---|---:|---|
| `js/app.js` | 103 | маршруты, шапка, плеер, `teardown` |
| `js/screens/menu.js` | 114 | список пространств |
| `js/screens/space.js` | 484 | холст, перетаскивание, связи, камера |
| `js/screens/node.js` | 582 | редактор текста, боковые панели, свиток |
| `js/db.js` | 200 | IndexedDB: записи и файлы |
| `js/ui.js` | 410 | DOM, окна, очистка HTML, blob-ссылки, файл, громкость |
| `js/calc.js` | 301 | парсер + виджеты кубиков и калькулятора |
| `js/zip.js` | 201 | zip без сжатия: запись, чтение, контрольные суммы |
| `js/backup.js` | 264 | сборка кодекса в файл и разбор обратно |
| `js/demo.js` | 197 | демо-сцена на пустом хранилище, один раз |

## 2. Поток данных

### 2.1. Открытие экрана

Единственный источник правды о том, что показано на экране, — адресная строка.

    клик по карточке
        └─> APP.go('#/n/ab12')        location.hash = '#/n/ab12'
                └─> событие hashchange
                        └─> APP.route()
                             1. вызывает teardown прошлого экрана
                                (снимает слушатели с document/window)
                             2. UI.releaseUrls()  — отзывает blob:-ссылки
                             3. разбирает хеш и зовёт NODE.render('ab12')
                                     │
                                     ├─> DB.getNode / getSpace / listAssets / listLinks
                                     │        (IndexedDB, всё асинхронно)
                                     └─> строит DOM и кладёт в #app одним
                                         replaceChildren — без промежуточных
                                         состояний и мерцания

Почему через `hashchange`, а не прямым вызовом: тогда «назад» в браузере,
перезагрузка страницы и ссылка на конкретный объект работают сами собой, без
единой строки дополнительного кода. Проверено: перезагрузка на `#/n/<id>`
открывает тот же объект с сохранённым текстом.

### 2.2. Правка текста — путь одного нажатия клавиши

    ввод символа в .doc-text (contenteditable)
        └─> 'input'
             ├─> updateEmpty()          показать/убрать подсказку-заглушку
             ├─> статус «сохраняю…»     видимая обратная связь сразу
             └─> saveDoc()  debounce 500 мс
                    ├─> serialize()     клон DOM, у <img> снимается src
                    │                   (в базу уезжает только data-asset)
                    ├─> DB.updateNode({ html, text })
                    ├─> DB.touchSpace() → updatedAt, по нему сортируется меню
                    └─> статус «сохранено», через 1.6 с гаснет

Смысл `serialize()`: в живом DOM у картинок стоят `blob:`-ссылки, которые
действительны только в текущей вкладке и умирают при перезагрузке. Хранить их
в базе — значит гарантированно получить битые картинки завтра. Поэтому в базу
уходит только `data-asset="<id>"`, а при открытии объекта `hydrateImages()`
достаёт файл из IndexedDB и подставляет свежую ссылку. Если файл удалён —
на его месте появляется честная пометка «⟨изображение удалено⟩», а не
сломанный значок.

### 2.3. Загрузка файла

    UI.pickFiles()                  один скрытый <input type=file> на всё приложение
        └─> DB.addAsset(nodeId, file, kind)
                 File кладётся в IndexedDB как есть — это Blob, без перекодирования
        └─> первый загруженный image становится обложкой карточки, если её не было
        └─> renderSide() + refreshMeta()   перерисовывается только боковая панель

### 2.4. Жизненный цикл `blob:`-ссылок

Каждая `URL.createObjectURL` держит файл в памяти вкладки, пока её явно не
отозвать. Поэтому все ссылки выдаёт `UI.blobUrl()` и складывает в реестр, а
`APP.route()` при каждом переходе вызывает `releaseUrls()` — реестр чистится
целиком.

Одно осознанное исключение: мини-плеер создаёт свою ссылку **мимо** реестра
(`URL.createObjectURL` напрямую в `app.js`) и сам её отзывает при смене трека
или закрытии. Иначе музыка обрывалась бы на каждом переходе между экранами —
а она должна играть поверх всех экранов.

### 2.5. Громкость: одна на всё приложение

Проигрывателей в приложении несколько: мини-плеер поверх экранов и по одному
`<audio>` на каждую запись в панели музыки. Каждый из них живёт недолго —
панель перерисовывается при любой правке, а мини-плеер создаётся заново при
первом запуске трека. Своя громкость у каждого означала бы, что уровень
сбрасывается на полный при переходе на соседний объект: посреди игры это
внезапный удар по ушам.

Поэтому уровень один на всё приложение и хранится отдельно от материалов:

    UI.bindVolume(audio)
        ├─ ставит новому проигрывателю общий уровень и признак «без звука»
        ├─ подписывается на volumechange
        │     └─> запоминает уровень (debounce 300 мс → localStorage)
        │     └─> раздаёт его остальным живым проигрывателям
        └─ кладёт элемент в реестр живых

Реестр чистится лениво: перед раздачей из него выбрасываются элементы, которых
уже нет в документе (`isConnected`). Отдельная уборка при перерисовке панели не
нужна — это тот же приём «одна точка ответственности вместо десятка мест», что
и с реестром `blob:`-ссылок.

Раздача защищена флагом: присвоение `volume` само порождает `volumechange`, и
без него обработчики зациклились бы.

## 3. Модель данных

Четыре хранилища IndexedDB, версия схемы 1:

| store | ключ | индекс | что лежит |
|---|---|---|---|
| `spaces` | `id` | — | `name, description, scratch, createdAt, updatedAt` |
| `nodes` | `id` | `spaceId` | `name, x, y, coverId, html, text, notes[]` |
| `links` | `id` | `spaceId` | `a, b` — id двух объектов, `label` |
| `assets` | `id` | `nodeId` | `kind, name, mime, size, blob` |

Связь — отдельная запись, а не поле внутри объекта. Так удаление объекта не
требует править чужие записи, а `listLinks(spaceId)` одним индексным запросом
отдаёт все нити плана.

Индексы здесь не украшение: без `nodes.spaceId` пришлось бы вычитывать все
объекты всех пространств и фильтровать в памяти. Индекс превращает это в один
запрос по ключу.

Каскадные удаления идут **одной транзакцией на все затронутые хранилища**
(`deleteSpace` открывает `spaces + nodes + links + assets` разом). Если что-то
падает посередине, транзакция откатывается целиком, и не остаётся ни объектов
без пространства, ни файлов без объекта. Обёртка `tx()` из `db.js` для этого
специально ловит исключение из колбэка и делает `abort()`.

Идентификаторы: `Date.now().toString(36) + 6 случайных символов`. Временная
часть впереди — записи естественно упорядочены по возрасту; случайный хвост
снимает коллизии при создании нескольких объектов в одну миллисекунду.

## 4. Почему IndexedDB, а не localStorage

Короткий ответ: в приложении лежат **файлы**, а localStorage умеет хранить
только строки и только синхронно.

Развёрнуто — четыре причины, каждая проверена замером. Цифры получены в
headless Chromium на машине разработки (`navigator.storage.estimate()` и
`performance.now()`, скрипт разовый); на другом железе и в другом браузере
абсолютные значения будут иными, соотношения — те же.

**1. Объём.** localStorage упёрся в `QuotaExceededError` на **4.94 МБ**.
IndexedDB на той же машине отдала квоту **2048 МБ** — на три порядка больше и
пропорционально свободному диску. Одна карта подземелья в PNG — это уже
несколько мегабайт; кампания на десяток сессий в 5 МБ не поместится в принципе.

**2. Формат.** localStorage хранит строки, значит файл пришлось бы держать в
base64. Замер: **×1.333 к размеру** (математический предел кодирования) и
**14 мс** на кодирование всего лишь 256 КБ. То есть 5-мегабайтная картинка
съела бы 6.7 МБ квоты — больше, чем всё доступное место. IndexedDB кладёт
`File`/`Blob` как есть: замер `blob instanceof Blob` после чтения — `true`,
перекодирования нет вообще.

**3. Синхронность.** `localStorage.setItem` останавливает главный поток:
запись 4 МБ заняла **25.5 мс**. Кадр при 60 fps — 16.7 мс, то есть одна такая
запись это гарантированно пропущенный кадр и заметный рывок. IndexedDB на том
же объёме отработала за **29.6 мс**, но асинхронно: главный поток всё это время
свободен, ввод не подтормаживает. Приложение сохраняет текст на каждом нажатии
клавиши (с задержкой в 500 мс), так что цена блокировки здесь не теоретическая.

**4. Запросы и транзакции.** В localStorage нет ни индексов, ни транзакций:
«достать объекты пространства X» означало бы прочитать и распарсить весь
JSON целиком, а каскадное удаление невозможно было бы сделать атомарным —
на середине операции данные остались бы битыми.

### Что всё-таки лежит в localStorage — и почему это не противоречие

Три ключа, все про вид и настройки, а не про содержимое:

    jm.cam.<spaceId>        { x, y, scale }        положение камеры на холсте
    jm.scratch.<spaceId>    '1' | '0'              открыт ли свиток заметок
    jm.volume               { level, muted }       громкость звука

Здесь localStorage выбран сознательно и по делу: данные крохотные, читаются
**синхронно при первом кадре** (камеру надо знать до отрисовки холста, иначе
карточки прыгнут; громкость — до того, как заиграет первый трек, иначе музыка
ударит на полной), а их потеря стоит ровно ничего — пользователь увидит
масштаб 100 % вместо 120 %. Все чтения обёрнуты в `try/catch`: если браузер
запретил хранилище, экран просто откроется со значениями по умолчанию.

Громкость сознательно не попадает в файл `.jm.zip`: это настройка слушателя,
а не материал кампании. Перенос кодекса на другую машину не должен менять там
уровень звука.

Принцип: **уровень хранения выбирается по цене потери данных**. Потерять
положение камеры не жалко — localStorage. Потерять текст кампании нельзя —
IndexedDB с транзакциями.

## 5. Кодекс одним файлом

Хранилище браузера пользователю не принадлежит: его сносит чистка данных сайта,
переустановка системы, режим инкогнито и — на телефонах — сам браузер под
нехватку места. Для кодекса, который мастер набивает месяцами, это главный
риск, и он не лечится выбором хранилища. Лечится он возможностью унести всё
одним файлом.

### Почему zip, а не JSON с base64

Очевидное решение — сложить всё в один JSON, а файлы закодировать в base64.
Оно отпадает по двум причинам:

1. **Размер и память.** Base64 раздувает двоичные данные на треть, и вся строка
   существует в памяти целиком, вдобавок к самим данным. Кампания с эмбиентом
   на 300 МБ превращается в 400 МБ текста поверх 300 МБ блобов.
2. **Непрозрачность.** Из такого файла ничего не достать без этой самой
   программы. А zip открывается двойным щелчком в любой системе: внутри лежит
   `codex.json` и папка `assets` с картинками под своими расширениями.

Второй довод перевесил бы даже без первого. Резервная копия, которую нельзя
прочитать ничем, кроме сломавшейся программы, — плохая резервная копия.

    codex.jm.zip
      codex.json          пространства, объекты, связи, пометки, разметка текста
      assets/<id>.bin     изображения, видео, музыка — байт в байт как загружены

Файлы кладутся методом STORE, без сжатия. Внутри почти всегда JPEG, PNG, MP3 и
MP4 — они уже сжаты своими форматами, и deflate отыграл бы единицы процентов в
обмен на реализацию всего алгоритма без зависимостей. Текст рядом с медиа
весит пренебрежимо мало.

Своя реализация zip (`js/zip.js`, 201 строка) — следствие правила «без
зависимостей». Формат простой ровно настолько, чтобы это было честной сделкой:
локальный заголовок, содержимое, опись в конце, CRC-32 на каждый файл. Не
поддерживается zip64, то есть архив до 4 ГБ и до 65535 файлов; выход за
границу заканчивается понятной ошибкой, а не битым файлом.

### Загрузка добавляет, а не заменяет

При загрузке все идентификаторы выдаются заново, а пространства встают рядом с
существующими. Так сделано осознанно: замена означала бы, что одно неверное
нажатие стирает текущий кодекс, а промах при добавлении даёт дубль — заметный
и удаляемый.

Из перевыдачи идентификаторов следует работа, которую легко забыть: ссылки
внутри данных надо переписать. Их три вида, и все три переписываются в
`apply()`:

| ссылка | где живёт | что делает загрузка |
|---|---|---|
| `coverId` | поле объекта | подставляет новый идентификатор файла |
| `a`, `b` у связи | запись связи | подставляет новые идентификаторы объектов |
| `data-asset` | атрибут `<img>` внутри разметки текста | переписывает разбором через `DOMParser` |

Третий — самый неочевидный: картинки внутри текста хранятся не адресом, а
ссылкой на файл в хранилище (см. 2.4), поэтому разметку приходится разбирать и
собирать заново. Пропусти этот шаг — и текст загрузится, а картинки в нём
молча превратятся в «⟨изображение удалено⟩».

### Где проходит граница с настольной версией

[Настольная версия](https://github.com/KennyS44/Journeyman-Desktop) читает и
пишет тот же формат — это и есть способ переехать из браузера в программу.
Общего кода при этом ровно столько же, сколько раньше: `zip.js`, `backup.js`,
экраны и оформление лежат в обоих проектах дословно одинаковыми.

Расходится одно: куда девать собранные байты. В браузере это ссылка с
атрибутом `download`, в программе — системный диалог сохранения и запись на
диск. Развилка спрятана в `UI.saveFile` и выглядит как проверка наличия моста:

    const bridge = window.journeyman;
    if (bridge && bridge.saveFile) ...        // настольная версия
    // иначе — обычная ссылка на скачивание

В браузере моста нет, условие не выполняется, и файл остаётся общим. Тот же
приём — единственная строчка условия вместо второй копии файла — используется
для пунктов меню «Файл» настольной версии.

Мелочь, которая стоила отладки: имя скачиваемого файла в браузере переводится в
латиницу. Кириллицу в атрибуте `download` часть сборок Chromium отбрасывает
целиком — файл приходит с именем «download» и без расширения. В настольной
версии этого не требуется: имя уходит в системный диалог как есть.

### Чем за это заплачено

Архив собирается в памяти целиком: сначала блобы из хранилища, потом готовый
буфер. Пиковый расход — примерно два объёма кодекса. Для сотен мегабайт музыки
на слабой машине это может кончиться отказом, поэтому перед сборкой тяжёлого
кодекса программа честно предупреждает и спрашивает. Правильное решение —
потоковая запись через `TransformStream` и `showSaveFilePicker`, но оно
доступно не во всех браузерах и требует заметно больше кода; отложено
сознательно.

## 6. Почему рекурсивный спуск, а не `eval`

Калькулятор принимает `2d6+3`, `(d20+5)*2`, `4к6`. Соблазн написать
`eval(expr.replace(...))` есть всегда — вот шесть причин, по которым в проекте
стоят 110 строк разбора.

Грамматика целиком (`js/calc.js`), приоритеты заданы вложенностью правил:

    expr    := term (('+' | '-') term)*
    term    := unary (('*' | '/') unary)*
    unary   := ('+' | '-') unary | primary
    primary := 'd' number              // d20 — один кубик
             | number ['d' number]     // 2d6 или просто число
             | '(' expr ')'

**1. Безопасность.** `eval` исполняет строку пользователя как код с полными
правами страницы — а на этой странице лежит вся база кампаний и открыт
IndexedDB. Строка из буфера обмена, вставленная в поле калькулятора, получила
бы доступ ко всем данным пользователя. Парсер физически не может ничего
исполнить: на выходе у него число, а не код. Побочная выгода — приложение
остаётся совместимым с `Content-Security-Policy` без `unsafe-eval`.

**2. `2d6` — это не JavaScript.** Свой диалект нужен в любом случае: кубики,
`к`/`д` вместо `d`, запятая как десятичный разделитель, знаки `×` `÷` `−` с
клавиатуры и из буфера. С `eval` пришлось бы городить цепочку `replace` —
то есть всё равно писать разбор, только неявный, дырявый и непроверяемый.

**3. Ошибки на языке пользователя.** `eval('2+')` бросает
`SyntaxError: Unexpected end of input`. Парсер говорит «Выражение
обрывается», «Не закрыта скобка», «После d нужно число граней», «Непонятный
символ «$»» — и показывает это прямо под полем ввода.

**4. Нужна не сумма, а разбор броска.** Мастеру важно видеть каждый кубик:
`2d6: 4 + 3`. `evaluate()` возвращает `{ value, rolls: [{ spec, dice, sum }] }`
— побочный результат разбора, который `eval` дать не может в принципе.

**5. Предохранители.** `10000d6` в наивной реализации подвесит вкладку;
`eval('while(1){}')` — тем более. В парсере стоят жёсткие пределы: не больше
**200** кубиков за бросок и не больше **d1000**, с внятным сообщением вместо
зависания.

**6. Тестируемость.** `evaluate` — чистая функция без DOM, поэтому её гоняет
`node tests/calc.test.js`: 48 проверок по шести разделам — приоритет операций,
унарные минусы, типографские знаки, ошибки разбора, границы кубиков, формат
вывода. Броски проверяются по 200 прогонов на границы диапазона.

Тесты сразу окупились: они нашли реальный баг. Выражение `1.2.3` считалось как
`1.2` — токенайзер собирал строку из цифр и точек, а `parseFloat` молча
отбрасывал хвост, поэтому проверка на `NaN` никогда не срабатывала. Теперь
токен числа сверяется с шаблоном `^(\d+(\.\d*)?|\.\d+)$` и такое выражение
честно падает с «Непонятное число». С `eval` этот случай не всплыл бы вовсе:
`1.2.3` там — синтаксическая ошибка с непонятным текстом, а не тихо неверный
ответ.

## 7. Маршрутизация и уборка за экраном

Экран, который вешает слушатели на `document` или `window`, обязан их снять —
иначе после десяти переходов на клавишу Esc отвечают десять мёртвых обработчиков.
Договор простой: экран в конце `render()` отдаёт `APP.setTeardown(fn)`, а
`route()` вызывает его перед следующим экраном.

Кто что снимает: `space.js` — `keydown` (Esc выходит из режима связи);
`node.js` — `selectionchange` (запоминание места ввода) и `resize`
(рамка вокруг картинки). `menu.js` не вешает ничего глобального и teardown не
регистрирует.

Роутер запускается по `DOMContentLoaded`, а не сразу при загрузке `app.js`.
Благодаря этому порядок `<script>` в `index.html` ни на что не влияет: к моменту
первого `route()` все три экрана уже объявлены.

## 8. Безопасность текста

Редактор — `contenteditable`, то есть в него можно вставить что угодно из
буфера обмена, включая `<script>` и `onerror=`. Весь входящий HTML — и при
вставке, и при чтении старой записи из базы — проходит через
`UI.sanitizeHtml()`: разбор в инертный документ через `DOMParser` (в нём
картинки не грузятся и скрипты не исполняются), затем копирование по
белому списку тегов и атрибутов. Всё, чего нет в списке, отбрасывается;
содержимое неизвестного тега сохраняется, сам тег — нет.

У `img` выживают только `data-asset`, `alt` и числовой `width`; у `a` — только
`href` со схемой `http`, `https` или `mailto`. Ни одного атрибута `on*`,
ни `style`, ни `srcdoc` в белом списке нет.

## 9. Известные ограничения

Честный список: что я знаю про слабые места своего кода и что менял бы дальше.

- **`await` внутри транзакции IndexedDB.** `tx()` позволяет писать
  последовательные запросы через `await`. Это держится на том, что транзакция
  живёт, пока продолжение остаётся в микрозадаче; любой `await`, уходящий в
  макрозадачу (таймер, сетевой запрос), транзакцию закроет. Сейчас такого кода
  нет и всё работает, но это хрупкое место, а не гарантия языка.
- **`document.execCommand` объявлен устаревшим.** Замены, работающей везде, нет:
  альтернатива — писать собственный движок форматирования поверх Selection API.
  Для нынешнего объёма это не окупается, но однажды сломается.
- **Свой `sanitizeHtml` вместо DOMPurify.** Проект принципиально без
  зависимостей, а белый список короткий и закрытый. В продукте с деньгами взял
  бы проверенную библиотеку — здесь цена ошибки ограничена собственными
  данными пользователя в его же браузере.
- **Данные привязаны к origin.** `file://` и `http://localhost` — разные
  хранилища; синхронизации между устройствами нет и не может быть без сервера
  (решение осознанное: бекенд обсуждался и был отклонён). Переносить материалы
  между браузерами, машинами и настольной версией приходится вручную — файлом
  `.jm.zip` (см. 5).
- **Экспорт собирается в памяти целиком.** Пик — около двух объёмов кодекса.
  Перед сборкой тяжёлого архива программа предупреждает, но по-настоящему это
  лечится потоковой записью (см. 5).
- **IndexedDB можно вытеснить.** `navigator.storage.persist()` не запрашивается,
  а `DB.estimate()` написана и нигде не используется — браузер вправе очистить
  базу под нехватку места, и пользователь об этом не узнает. Ближайший
  очевидный шаг после экспорта.
- **Один слот `teardown`.** Экранов три и вложенных экранов нет, поэтому
  достаточно; для вложенных представлений понадобился бы стек.
- **Изображения хранятся в исходном размере.** Фотография с телефона на 8 МБ
  ляжет в базу целиком. Уменьшение через `canvas` при загрузке — понятное
  улучшение, пока не сделано.

## 10. Что спросят на собеседовании

**«Почему без фреймворка?»** Три экрана, один пользователь, ноль сетевых
запросов. React принёс бы виртуальный DOM и сборку ради задачи, которая
решается `replaceChildren` и хешем в адресной строке. Зато проект открывается
двойным щелчком по `index.html` и не ломается при смене версии тулинга.

**«Как перерисовывается интерфейс без реактивности?»** Явно и по месту. Экран
целиком собирается в `render()`, а мелкие обновления адресные: `renderSide()`
трогает только боковую панель, `drawWires()` — только SVG со связями,
`refreshMeta()` — одну строку счётчиков. Перетаскивание карточки вообще не
трогает DOM-дерево: меняются `style.left/top` и пересчитываются линии.

**«Что будет при потере данных браузером?»** Чистка данных сайта убьёт всё —
это цена работы без сервера, и она названа пользователю прямо в README.
Смягчение — экспорт кампании файлом; в бэклоге первым пунктом.

**«Где узкое место по производительности?»** `drawWires()` пересобирает весь
SVG на каждый кадр перетаскивания: O(число связей) создания элементов. На
десятках объектов незаметно, на сотнях — начнёт греть. Правильный шаг —
обновлять атрибут `d` у существующих путей вместо пересоздания.

**«Почему тесты только на парсер?»** Потому что это единственная часть с
нетривиальной логикой и без DOM — там ошибка тихая и дорогая (что тесты и
подтвердили, найдя `1.2.3` → `1.2`). Экраны проверяются прогоном в headless
Chromium: создать пространство → объект → текст → перезагрузка → связи →
масштаб, с проверкой, что консоль чистая.
